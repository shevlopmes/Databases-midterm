# Решения проекта

Этот файл отделяет явно выбранные пользователем границы проекта от
реализационных решений первой версии. Последние можно пересматривать:
они не означают, что пользователь заранее согласился со всеми деталями.

## Границы, выбранные вместе

- Пишем собственную специализированную БД для бронирований.
- Язык — Python.
- Один процесс и последовательное исполнение записей.
- Пользователь бронирует конкретный столик на конкретный слот; гостей не считаем.
- Открываем весь батч одной транзакцией.
- В текущей версии можно отменить одну свою бронь; история сохраняется, слот освобождается.
- HTTP-записи требуют заранее выданного персонального токена.
- Служебные команды доступны только через доверенный локальный CLI.

## 1. Последовательное исполнение

Причина: проще объяснить и проверить неделимость проверки и захвата слота.
Синхронный HTTPServer вызывает движок в одном потоке. Между командами нет
совместного изменения состояния. Движок дополнительно проверяет владельца
по процессу и потоку, файловая блокировка запрещает второго владельца каталога.

Цена: медленная запись, долгий запрос или медленный клиент задерживают остальных.
Есть таймаут socket I/O, но нет полной защиты от медленных клиентов.
Модель не гарантирует порядок человеческих кликов и не является справедливой очередью.
При переполнении очереди соединений возможны ошибки транспорта.

На защите: «Мы ограничили параллелизм внутри БД. Внешние запросы остаются
конкурентными, а решение о владельце слота принимается последовательно».

## 2. Проверка уникальности внутри команды reserve

Инвариант: у каждого слота не более одного текущего владельца.
Сначала проверяем `_active`, затем сохраняем транзакцию и обновляем этот индекс.
Следующая команда не начнётся, пока текущая не закончится.
После ошибки записи движок прекращает обслуживать операции до восстановления.

Это замена механизму PostgreSQL UNIQUE в нашей собственной БД.
Универсального механизма SQL-ограничений здесь нет.

## 3. Append-only журнал и индексы в памяти

Каждая новая валидная команда вместе с результатом сохраняется одной JSON-строкой.
При запуске журнал проверяется и проигрывается заново. Состояние не является
вторым независимо обновляемым дисковым файлом: не требуется согласовывать
две физические копии данных при каждом commit.

Цена: весь рабочий набор и история запросов помещаются в память,
запуск требует воспроизведения истории, журнал не уменьшается.
Проверка пересечений при подготовке батча сортирует интервалы;
специализированного интервального индекса пока нет.

Локальные транзакции сохраняют формат `1`, а аутентифицированные HTTP-запросы
используют формат `2` с `actor_id`. Будущие изменения семантики потребуют
совместимого обработчика старой версии или явной миграции: нельзя незаметно
изменить смысл старых команд и продолжать проигрывать их как новые.

## 4. Подтверждение после fsync

Порядок: спланировать → записать → flush → fsync → применить в памяти → ответить.
Успешный ответ не предшествует синхронизации файла. Точка commit для работающего
движка — успешное завершение fsync; применение в памяти происходит до следующей
команды. Тест отдельно завершает процесс между синхронизацией и применением.

Полная запись может пережить сбой до ответа и даже до возвращения fsync.
При восстановлении такую запись принимаем. Клиент поэтому не может считать
таймаут доказательством отсутствия брони.

После проверки и воспроизведения журнала при открытии обязательно выполняем
новый fsync, даже если незавершённого хвоста нет. Только затем разрешаем
обслуживание запросов, включая ответы из истории идемпотентности.
Это исправляет ошибку первоначальной версии: полная, но ещё не синхронизированная
запись могла быть принята при запуске, а её повтор — получить успех без fsync.
Регрессионный тест завершает процесс после flush перед fsync и проверяет,
что при недоступной синхронизации новая БД не сможет подтвердить этот результат.

Цена: синхронизация на каждую новую команду ограничивает скорость.
Групповой commit мог бы увеличить пропускную способность, но изменит ожидание
и обработку ошибок. Это будущий decision point, а не скрытая оптимизация.
Аппаратные гарантии ограничены моделью сбоев, описанной в README.

## 5. Отделение незавершённой записи от повреждения

JSON экранирует переводы строк внутри значений; один физический перевод строки
завершает одну транзакцию. Незавершённый последний фрагмент отбрасываем.
Для каждой завершённой записи проверяем SHA-256, затем схему и соответствие
сохранённого результата предыдущему состоянию.

Цена: повреждённая завершённая запись блокирует открытие всей БД.
Мы предпочитаем явную ошибку скрытому пропуску потенциально подтверждённой операции.
Checksum не обнаруживает любую возможную потерю истории и не защищает от подделки.

Ошибка записи или fsync имеет неопределённый исход. Нельзя просто продолжить
работу с прежним состоянием памяти: в файле уже может лежать полная транзакция.
Нужно закрыть БД, устранить причину, открыть её заново и повторить прежнюю заявку.

## 6. Ключ идемпотентности относится к попытке

Одинаковый `request_id` и одинаковая нормализованная команда возвращают
сохранённый результат. Другие параметры с тем же ключом дают конфликт.
Для локальных команд ключ глобален в пределах каталога БД. Для HTTP ключ
ограничен парой `(user_id, request_id)`; пространства разделены. Клиенту удобно
генерировать UUID для каждой попытки. Автоматического срока хранения ключей нет.

Сохраняются и успешные результаты, и бизнес-отказы. Некорректный ввод,
конфликт самого ключа и инфраструктурные ошибки результатом бизнес-команды
не являются и отдельно не записываются.

Цена: каждая новая проигравшая заявка тоже увеличивает журнал и требует fsync.
Польза: после отмены повтор старой отклонённой заявки не захватит слот
неожиданно. Для новой осознанной попытки нужен новый ключ.

## 7. Публикация через состояние батча

`prepare_batch` целиком создаёт черновик. `publish_batch` одной транзакцией
меняет его состояние. `list_slots` и `reserve` проверяют состояние батча.
Не требуется последовательно переключать доступность каждого слота.

Цена: первая версия не позволяет менять опубликованный батч, отзывать публикацию,
редактировать слоты или открывать часть батча. Автоматического планировщика нет.
Повтор публикации с новым ключом возвращает успех, не создавая новых слотов.

## 8. Временная модель

Все даты имеют явное смещение и нормализуются в UTC. Интервалы полуоткрытые:
столик можно использовать с 18 до 20 и затем с 20 до 22.
Пересечения запрещены во всех батчах, включая черновики.

Цена: нельзя подготовить два альтернативных расписания с пересечениями.
Бронирование не проверяет текущее время: правила для прошлых дат и окончания
приёма заявок потребуют отдельного решения, зависящего от бизнес-сценария.

## 9. Удаление брони через атомарную отмену

Выбрали логическое удаление: команда `cancel` освобождает слот и сохраняет
историю создания брони. Причина — возможность восстановить состояние и объяснить,
почему прежняя заявка уже не владеет столиком. Физическое удаление записи из
append-only журнала потребовало бы отдельного механизма переписывания истории.

Минимальный интерфейс: `cancel(reservation_id, user_id)` через существующие
`POST /commands` и CLI `command`. Идентификатор брони — положительное целое число;
булевы значения и числа с плавающей точкой не принимаются. Проверяем существование
брони, совпадение владельца и отсутствие предыдущей отмены.

Отменяем по идентификатору брони. Это существенно: после отмены и нового
бронирования тот же слот принадлежит другой записи с новым идентификатором.
Запоздавшая старая отмена не должна освобождать столик нового владельца.
Идентификаторы броней после отмены не переиспользуются.

Состояние разделено на три части:

- `_reservations`: неизменная история создания броней;
- `_active`: текущий владелец каждого слота;
- `_cancelled`: идентификатор отменённой брони и UTC-время отмены.

В `inspect` к броням добавлено поле `cancelled_at`: `null` для действующей брони
или время отмены. Отдельный enum статусов пока не нужен: переход только один,
от действующей брони к отменённой. `check` дополнительно считает
`cancelled_reservations`; общее `reservations` по-прежнему включает всю историю.

Отмена использует тот же commit: проверить → записать команду и результат →
flush → fsync → обновить индексы → ответить. Удаление из `_active` и регистрация
в `_cancelled` выполняются до следующего запроса и восстанавливаются одной
транзакцией. При ошибке записи или fsync БД прекращает обслуживание до
восстановления, как и при бронировании.

Повторы обрабатываются существующей историей идемпотентности:

- Прежний `request_id` с прежней командой возвращает прежний результат отмены
  без новой записи и изменения текущего владельца слота.
- Новый ключ для уже отменённой брони получает бизнес-отказ
  `reservation_already_cancelled` (`409`).
- Отмена чужой брони получает `reservation_not_owner`, неизвестной —
`reservation_not_found`; в движке это бизнес-отказы. HTTP возвращает `403`
для чужой брони, `409` для неизвестной или уже отменённой.
- Повтор прежней успешной заявки `reserve` после отмены возвращает исторический
  успех создания. Он не возобновляет бронь и не сообщает её текущее состояние.
- Повтор прежней проигравшей заявки после освобождения слота возвращает прежний
  отказ. Для новой попытки забронировать нужен новый ключ.

Сохранены прежний ответ `reserve` и чтение контейнера транзакции `1`.
Добавление полей в сохранённый результат `reserve` изменило бы его проверку
при воспроизведении старых журналов. Поэтому метаданные отмены ведём отдельно.
Новая версия читает старые журналы без миграции; старый движок не поддерживает
новые команды и аутентифицированные записи версии 2.

Цена решения: отмена освобождает столик, но не уменьшает журнал и объём истории
в памяти. Для этого этапа нет массовой отмены, административного удаления,
восстановления отменённой брони, штрафов и дедлайнов. Отменить можно в любое время.
Первоначальная уязвимость подмены `user_id` закрыта этапом 12: HTTP получает
пользователя из токена и отклоняет это поле в JSON. Доверенный локальный CLI
по-прежнему принимает явный `user_id`: оператор с доступом к файлам БД
находится за пределами защиты от сетевого клиента.

Проверяли по этапам: исходные тесты → тесты поведения отмены до реализации →
проверки движка → CLI и HTTP → полный набор. Добавлены проверки освобождения
и повторного захвата слота, владельца, повторов, прежних результатов `reserve`,
ошибки fsync, обрыва отмены на каждой позиции байта и завершения процесса между
синхронизацией и обновлением памяти. Конкурентные HTTP-клиенты проверяют повторы
одной отмены и смешанные старые отмены с новыми бронированиями.

## 10. Диагностика отделена от восстановления

`check` открывает существующий журнал для чтения, проверяет его и полностью
воспроизводит состояние в памяти, не меняя содержимого файлов. Сохраняем
единственную реализацию чтения журнала и проверки бизнес-согласованности:
она используется и диагностикой, и обычным открытием БД.

Восстановление состоит из двух фаз: сначала завершить все проверки, затем
в обычном режиме обрезать незавершённый хвост и выполнить fsync.
Диагностика останавливается после первой фазы и сообщает размер хвоста.
Она не выдаёт результаты команд, даже ранее сохранённых, как подтверждение
их синхронизации с диском. `execute` в диагностическом режиме запрещён.

Цена: для согласованного чтения нужна исключительная блокировка, поэтому
перед проверкой приходится остановить сервер. Проверка не является
непрерывным мониторингом работающей БД и требует всей истории в памяти.
Файл `owner.lock` должен уже существовать; для его блокировки используется
открытие с правами чтения и записи без записи новых байтов.

Коды завершения: 0 — целый журнал, 1 — незавершённый хвост, 2 — ошибка проверки
или открытия. Никакого автоматического исправления повреждённых завершённых
записей нет. Существующие каталоги читаются без миграции; поддерживаются
старые записи версии 1 и новые записи версии 2.

Дополнительно сравниваем сохранённый результат с ожидаемым в каноническом JSON,
чтобы проверить типы: в Python `True == 1`, а для идентификатора брони эти
значения не взаимозаменяемы. Это проверка корректности записей, а не новый
формат или изменение бизнес-правил.

## 11. Проверка после добавления отмен

Исходные 46 тестов проходят. При проверке HTTP-границы воспроизведены две ошибки:

- Некорректный request target, например `http://[`, вызывал ValueError при
  разборе URL до блока обработки ошибок. Клиент получал разрыв соединения
  без JSON-ответа. Теперь получит `400 invalid_request`; следующий корректный
  запрос обслуживается. Потери записанных данных из-за этого не обнаружено.
- `NaN` и бесконечность принимались как положительный таймаут: сравнения с нулём
  недостаточно. При настройке принятого сокета такие значения недопустимы.
  Теперь проверяем конечность числа до запуска сервера. Значение по умолчанию
  5 секунд не менялось; CLI сообщает об ошибке конфигурации без traceback.

Добавлены регрессионные тесты для некорректного URL, конструктора сервера и CLI.
Дополнительный воспроизводимый проверочный сценарий: seed 20261125, 240 команд
и повторов, 12 перезапусков. Проверялись отсутствие двойных владельцев,
согласованность истории с текущим владением, стабильность результатов повторов
и равенство состояния до и после перезапуска. Нарушений не обнаружено.
Эти параметры описывают эксперимент, а не ограничения или настройки движка.

На момент той проверки в изолированном сервере подтверждалось: без аутентификации
`add_table`, `prepare_batch`, `publish_batch` возвращают `200`. Это известный
пробел в разграничении прав. Он и подмена `user_id` закрыты этапом 12.
Проверка не доказывает отсутствие
всех ошибок; аппаратные отказы, произвольное повреждение файлов и публичное
развёртывание остаются за пределами текущих гарантий.

## 12. Реализованная аутентификация персональными токенами

Явно выбрано пользователем:

- Заранее выданные персональные токены для нескольких пользователей.
- Служебные команды `add_table`, `prepare_batch`, `publish_batch` доступны
  только через доверенный локальный CLI, без токена администратора в HTTP API.

Ниже описана текущая реализация. Предыдущие предупреждения о свободной подмене
`user_id` и вызове служебных HTTP-команд сняты после проверок защиты.

### Граница доверия и порядок обработки

1. HTTP получает `Authorization: Bearer <token>`.
2. Компонент аутентификации проверяет токен и создаёт доверенный контекст
   с устойчивым `user_id`. При неверном или отсутствующем токене возвращает `401`.
3. Сервис клиентских команд разрешает только `reserve` и `cancel`.
   Служебные команды по HTTP отклоняются, даже с действующим персональным токеном.
4. Внешний JSON больше не принимает `user_id`. При его наличии возвращается
   `400`, чтобы подмена или использование старого клиента были заметны.
   Сервис самостоятельно подставляет подтверждённый идентификатор во внутреннюю
   команду движка. Проверка принадлежности брони остаётся в движке.
5. Лишь затем обрабатываются идемпотентность и транзакция.

`GET /slots` оставлен публичным: он показывает только опубликованные
слоты и доступность, без данных владельцев. Доверенный CLI по-прежнему имеет
доступ к файлам БД; персональные токены не защищают от оператора с таким доступом.

Разделение компонентов: HTTP разбирает протокол, небольшой auth-компонент
устанавливает личность, сервис ограничивает операции, движок проверяет
бизнес-инварианты и выполняет commit. Новые потоки или процессы не требуются.
Это позволяет позднее заменить способ входа, сохранив логику бронирования.

### Хранение и жизненный цикл токенов

- Генерация: `secrets.token_urlsafe(32)`, то есть 32 случайных байта, 256 бит
  случайности. Это явный параметр стойкости, а не неявный default библиотеки.
- Выдача через локальный инструмент вручную созданному пользователю; секрет
  показывается один раз и передаётся ему отдельно.
- Команды: `auth-issue --user-id ...` для выдачи/перевыпуска и
  `auth-revoke --user-id ...` для отзыва. По умолчанию реестр — `auth/users.json`,
  путь изменяется через `--auth-file`. Папка `auth/` исключена из Git.
- Отдельный конфигурационный файл с `user_id` и SHA-256 verifier токена.
  Исходный токен не хранить рядом с хешем, в журнале транзакций, Git или логах.
  Сравнение verifier выполнять через `compare_digest`.
- Сервер загружает конфигурацию при запуске. Отсутствующий или некорректный
  файл должен останавливать запуск, а не включать режим без аутентификации.
- Для минимального локального демо реализован ручной отзыв/перевыпуск без
  автоматического TTL: изменить конфигурацию и перезапустить сервер.
  Цена — нет немедленного отзыва на работающем сервере и автоматического
  истечения украденного токена. Это осознанная граница локального демо;
  TTL и динамический отзыв оставлены за пределами выбранного объёма.
- Замена токена сохраняет `user_id`: брони принадлежат пользователю, а не строке
  его текущего секрета. Передача bearer-токена даёт доступ от имени владельца;
  за пределами локального эксперимента требуется защищённый транспорт HTTPS.

### Идемпотентность и восстановление

Проверка действительности токена должна выполняться на КАЖДОМ запросе, в том
числе повторном. Кеш успешного ответа не должен обходить отзыв доступа.
Ключ ограничен парой `(user_id, request_id)`: одинаковые ключи
разных клиентов не должны конфликтовать или открывать чужие результаты.
Заменённый токен того же пользователя должен видеть прежнюю историю попыток.

Этот decision point для журнала решён так: `Database.execute` для доверенного
CLI сохраняет версию 1 и пространство ключей `(None, request_id)`.
`Database.execute_user` для доверенного сервиса сохраняет версию 2 с дополнительным
`actor_id` и пространством `(actor_id, request_id)`. Повторный вызов другого
пользователя не может прочитать или занять чужой ключ. В версии 2 допустимы
только `reserve`/`cancel`, `command.user_id` обязан совпадать с `actor_id`.

При запуске читаются обе версии. Старые записи не переписываются; в новом HTTP
пространстве старый глобальный ключ не продолжает прежнюю попытку. Это явное
ограничение совместимости протокола: после перехода используй новые ключи.
Владельцы существующих броней и старые CLI-повторы сохраняются. Старые движки
не читают версию 2, автоматического downgrade нет.

`execute_user` — внутренний доверенный вход, он не проверяет секрет. Токен
проверяет HTTP-слой через `AuthStore`, а `CommandService` ограничивает набор
операций и подставляет подтверждённый `user_id`. CLI и код с прямым доступом
к движку/файлам остаются доверенной административной границей.

В журнал записывается подтверждённый `user_id`, а не токен. При восстановлении
старых транзакций нельзя заново проверять текущие токены: отзыв токена не должен
делать уже сохранённую историю нечитаемой. Replay восстанавливает результаты,
проверка доступа применяется к новым внешним обращениям.

Реестр credentials имеет собственную версию `1`: это независимый формат
`{"version": 1, "users": [{"user_id": "...", "token_sha256": "..."}]}`.
Дубли пользователей или verifiers отклоняются. Обновление защищено файловой
блокировкой и атомарной заменой после fsync; при ошибке замены прежний реестр
сохраняется. Пустой список пользователей означает отсутствие разрешённых
HTTP-записей, а не отключение аутентификации.

### Реализованные проверки

- Нет токена, неверный токен, неоднозначные заголовки, некорректная конфигурация.
- Подстановка `user_id` в JSON отклоняется; токен Боба не отменяет бронь Алисы.
- Служебные команды запрещены через HTTP; локальный CLI продолжает работать.
- Повтор запроса проверяет доступ до чтения кеша; отзыв токена закрывает и повторы.
- Одинаковый `request_id` у разных пользователей не создаёт конфликтов между ними.
- Старые журналы и уже существующие владельцы броней сохраняют смысл.
- Токены отсутствуют в журнале, диагностических ответах и логах.
- Генератор нагрузки использует токены, однопоточный движок сохраняет гарантии.

Генератор получает отдельный приватный `--tokens-file` с исходными клиентскими
токенами, распределяет обращения между ними и не выводит секреты. В проверенном
прогоне 20 одновременных заявок дали одну бронь и 19 отказов. Это проверка
корректности, а не обещание промышленной пропускной способности.

### Граница итоговой версии курсовика

На этом завершаем функциональный объём: публикация, конкурентное бронирование,
отмена, идемпотентность, собственный журнал/восстановление и персональные токены.
Не добавляем регистрацию, пароли, OAuth/JWT, роли администраторов HTTP, TTL,
репликацию и снимки состояния. Остаются известные компромиссы: память под
всю историю, растущий журнал, один обработчик, локальный HTTP без TLS и ручное
управление токенами. Перед защитой нужны воспроизводимая демонстрация,
полный прогон тестов и объяснение этих ограничений; оценка зависит от критериев курса.

Итоговая проверка на Windows / Python 3.13: `python -m unittest discover -q` —
72 теста, все прошли. Отдельно пройден сценарий из README с реальной выдачей
токенов через PowerShell, сохранением клиентского файла, запуском HTTP,
20 одновременными обращениями, отказом в чужой отмене, своей отменой,
запретом публикации по HTTP, отзывом токена и перезапуском. Смешанный журнал
проверен после завершения сервера; секреты в нём отсутствовали. Старый
`demo-data` формата 1 также прошёл проверку без изменения содержимого.

## 13. Сценарий короткой записи

`scripts/video_demo.py` — клиентский демонстратор существующей реализации,
а не новый вариант движка. Он работает через настоящий HTTP, отдельные
персональные токены и отдельный каталог `data/video-demo/` для каждого запуска.
Токены остаются в памяти; на диске сохраняются verifiers, журнал и публичный
отчёт. Продуктовые команды и гарантии БД не менялись.

Демо показывает публикацию, 20 конкурентных обращений от двух пользователей,
одного победителя, повтор заявки, чужую/свою отмену, повторный захват слота,
принудительное завершение собственного процесса сервера и восстановление.
Любой неожиданный результат завершает демонстрацию ошибкой.
При обычном запуске переходы по Enter, `--auto` предназначен для репетиции
и автоматической проверки. Нет задержек, изображающих скорость сервера.

Важное ограничение текущей архитектуры: CLI-администрирование офлайн,
поскольку файл БД принадлежит единственному процессу. Поэтому публикация
показывается до запуска HTTP. Для публикации без остановки сервера понадобился
бы отдельный доверенный канал к единственному обработчику; это за пределами
зафиксированного объёма. Открывать служебные команды всем клиентам ради демо нельзя.

Речь и тайминг 1:40–1:55 находятся в `VIDEO_DEMO.md`. Параллелизм используется
только в клиентском генераторе; запись остаётся последовательной. Проверяется
сбой процесса, аппаратные гарантии не расширяются.

После добавления демонстратора полный `python -m unittest discover -q`:
73 теста, все прошли. Его интеграционный тест проверяет настоящий HTTP,
сохранённый отчёт, восстановление данных, отсутствие вывода секретов и
освобождение файлов после завершения серверных процессов.

## Первичные источники

- Python `socketserver`: синхронная обработка запросов:
  https://docs.python.org/3.13/library/socketserver.html
- Python `os.fsync`: синхронизация файла, перед ней требуется flush буфера:
  https://docs.python.org/3.13/library/os.html#os.fsync
- Python `msvcrt.locking`: блокировка диапазона файла на Windows:
  https://docs.python.org/3.13/library/msvcrt.html#msvcrt.locking
- SQLite: смысл атомарного commit и модель аппаратных сбоев:
  https://www.sqlite.org/atomiccommit.html
- Redis persistence: восстановление из append-only журнала и компромиссы fsync:
  https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/
- OWASP Authorization: разграничение аутентификации и прав, проверка каждого запроса:
  https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html
- OWASP Session Management: случайные токены и хранение односторонних verifier:
  https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
- Python secrets: генерация токенов и явная длина случайного секрета:
  https://docs.python.org/3.13/library/secrets.html
- RFC 6750: передача bearer-токена через Authorization и требования к транспорту:
  https://www.rfc-editor.org/rfc/rfc6750

Мы используем эти материалы для понимания механизмов. Реализация не повторяет
полный алгоритм SQLite или Redis и не наследует их гарантии автоматически.

# Restaurant DB: учебная база бронирований

Учебная специализированная база данных для бронирования конкретного столика
на заранее заданный слот. Python 3.11+, только стандартная библиотека.
PostgreSQL, SQLite и Redis внутри не используются.

HTTP-записи защищены персональными токенами. Пользователь определяется сервером;
передавать `user_id` в JSON нельзя. Подготовка расписания и публикация доступны
только через доверенный локальный CLI. Просмотр опубликованных слотов публичный.

**ЛОКАЛЬНОЕ УЧЕБНОЕ ДЕМО: ХРАНИ ТОКЕНЫ В СЕКРЕТЕ. ДЛЯ РАБОТЫ ПО СЕТИ НУЖЕН HTTPS.
ОТЗЫВ И ПЕРЕВЫПУСК ТОКЕНА ВСТУПАЮТ В СИЛУ ПОСЛЕ ПЕРЕЗАПУСКА СЕРВЕРА.**

Один процесс владеет данными. Один поток последовательно выполняет команды.
HTTP-клиенты могут обращаться одновременно, но движок не выполняет записи
параллельно. Успех бронирования подтверждается после записи журнала и `fsync`.

## Быстрый запуск

Открой PowerShell:

```powershell
cd C:\Users\Maxim\Documents\restaurant-db
python -m restaurant_db demo --data demo-data
```

Демо создаст два столика, подготовит и опубликует батч, забронирует слот за
Алисой, отклонит заявку Боба и повторит заявку Алисы. Затем заново откроет
БД и покажет восстановленные данные. Повторный запуск с тем же каталогом
вернёт сохранённые результаты: идентификаторы заявок демо постоянные.
Даты 2030 года — фиксированные демонстрационные данные.

Просмотр всех данных, включая черновики:

```powershell
python -m restaurant_db inspect --data demo-data
```

## Проверка журнала без изменения данных

Останови сервер, если он использует проверяемый каталог, затем выполни:

```powershell
python -m restaurant_db check --data demo-data
```

Команда проверяет JSON, контрольные суммы, версию транзакций, типы сохранённых
результатов и бизнес-правила при полном воспроизведении истории. Возвращает
число записей, размер проверенного префикса, размер незавершённого хвоста
и количество восстановленных сущностей.

Коды завершения:

| Код | Что означает | Что происходит с файлами |
|---|---|---|
| `0` | Все записи прошли проверку, `status: ok` | Содержимое не меняется |
| `1` | Найден незавершённый хвост, `status: incomplete_tail` | Хвост остаётся на месте |
| `2` | Повреждение, неизвестная версия, занятый каталог или ошибка доступа | Проверка завершается ошибкой |

`check` использует существующие `transactions.jsonl` и `owner.lock`, не создаёт
пустую БД при ошибке в пути и не выполняет `fsync`. Для согласованной проверки
берёт ту же исключительную блокировку каталога, что и сервер. Поэтому права
на открытие `owner.lock` для чтения и записи по-прежнему нужны, хотя его
содержимое не меняется. Другие программы не должны изменять файлы в обход блокировки.

Обычное открытие БД, в том числе через `inspect`, выполняет восстановление:
сначала проверяет весь журнал, затем обрезает только незавершённый хвост и
синхронизирует файл. После этого можно обслуживать запросы. При ошибке
синхронизации БД не открывается.

Разделение намеренное: диагностика сообщает о состоянии файла, восстановление
меняет его. Успешный `check` подтверждает внутреннюю согласованность журнала,
но не доказывает, что ранее был выполнен `fsync` или что оборудование сохранит
файл при отключении питания. Режим `Database(..., read_only=True)` предназначен
для диагностики; команды записи и повторы бизнес-заявок в нём запрещены.

Установка пакетов не требуется. Команды запускаются из корня проекта.

## Токены и запуск HTTP-сервера

В PowerShell выдай персональные токены. Первичная выдача и перевыпуск используют
одну команду; повтор для того же `user_id` заменит его текущий токен:

```powershell
$alice = python -m restaurant_db auth-issue --user-id alice | ConvertFrom-Json
$bob = python -m restaurant_db auth-issue --user-id bob | ConvertFrom-Json
@{ alice = $alice.token; bob = $bob.token } | ConvertTo-Json | Set-Content -Encoding utf8 auth/client.tokens.json
```

`auth/users.json` содержит только SHA-256 verifiers. `auth/client.tokens.json`
в примере содержит исходные секреты для клиентов. Папка `auth/` исключена из Git.
Не публикуй содержимое или вывод `auth-issue`. Для своего пути передай
`--auth-file путь` в команды управления токенами и в `serve`; исключение
нестандартного пути из Git — ответственность оператора.

Для демонстрации используй свежий каталог данных.

В первом терминале подготовь отдельную БД и запусти сервер:

```powershell
python -m restaurant_db seed --data data/auth-demo
python -m restaurant_db serve --data data/auth-demo --auth-file auth/users.json
```

Без доступного корректного файла credentials сервер не запускается; режима
автоматического отключения аутентификации нет. Пустой список пользователей
разрешает публичное чтение слотов, но не даёт никому права записи.

Отзыв — отдельный сценарий после демонстрации ниже. Останови сервер,
отзови токен и снова запусти сервер:

```powershell
python -m restaurant_db auth-revoke --user-id alice
python -m restaurant_db serve --data data/auth-demo --auth-file auth/users.json
```

Автоматического TTL нет. Конфигурация загружается при запуске; уже работающий
сервер продолжает использовать прежние токены до перезапуска. Перевыпуск
сохраняет `user_id`, поэтому не меняет владельца существующих броней.
Конфигурация обновляется под файловой блокировкой через временный файл,
fsync и атомарную замену. Ошибочный файл не перезаписывается автоматически.

## Одновременные пользователи

Во втором терминале, также из папки проекта:

```powershell
python scripts/race.py --clients 20 --slot-id s1 --tokens-file auth/client.tokens.json
```

Для свежего опубликованного слота ожидается `reserved: 1`, `slot_taken: 19`.
Генератор распределяет обращения между токенами из файла: 20 обращений могут
приходиться на двух пользователей. Личность в JSON больше не передаётся.
Все клиенты начинают отправку после общего барьера. Потоки используются только
в генераторе нагрузки: сервер и движок остаются однопоточными.
Победитель определяется порядком обработки, а не порядком нажатия кнопок.

Второй независимый эксперимент можно провести со слотом `s2`:

```powershell
python scripts/race.py --clients 20 --slot-id s2 --tokens-file auth/client.tokens.json
```

Повторный тест уже занятого слота закономерно не получит победителя.
Для следующих прогонов используй новый каталог с данными или новые слоты.
Генератор отдельно считает ошибки транспорта; они не означают «слот занят».
Измеренная скорость локального демо не является оценкой промышленной мощности.
Остановить сервер можно через Ctrl+C. Пока сервер открыт, CLI не сможет
открыть тот же каталог: это намеренная защита от двух владельцев файлов.

## API

`GET /slots` возвращает только слоты опубликованных батчей и их доступность.
Этот ответ не удерживает слот за пользователем.

`POST /commands` требует заголовок `Authorization: Bearer <token>` и JSON:

```json
{
  "request_id": "alice-attempt-1",
  "command": {"op": "reserve", "slot_id": "s2"}
}
```

Пример для свежего `s2` (не запускай второй race-прогон перед ним):

```powershell
$tokens = Get-Content auth/client.tokens.json -Raw | ConvertFrom-Json
$headers = @{ Authorization = "Bearer $($tokens.alice)" }
$body = @{
    request_id = "alice-attempt-1"
    command = @{ op = "reserve"; slot_id = "s2" }
} | ConvertTo-Json
$booking = Invoke-RestMethod -Uri http://127.0.0.1:8080/commands -Method Post -Headers $headers -ContentType "application/json" -Body $body
$booking
```

Ответы: `200` — успешная команда, `401` — нет действующего токена, `403` — нет
прав на операцию или чужую бронь, `409` — бизнес-отказ или конфликт ключа
идемпотентности, `400` — некорректный ввод, `503` — требуется восстановление БД.
Внутри ответа есть поле `code`, например `reserved`, `slot_taken`,
`batch_not_published` или `idempotency_conflict`.
При повторе успешной заявки ответ снова `200`, с той же бронью.

Если ответа нет или пришёл `503`, результат может быть неизвестен. После
восстановления повтори запрос с прежним `request_id` и прежней командой.
Подтверждать пользователю создание брони до успешного ответа нельзя.
После определённого бизнес-отказа новая осознанная попытка получает новый ключ.

Поддерживаемые команды:

| `op` | Поля команды | Доступ |
|---|---|---|
| `add_table` | `table_id`, `name` | Только CLI |
| `prepare_batch` | `batch_id`, `slots` | Только CLI |
| `publish_batch` | `batch_id` | Только CLI |
| `reserve` | `slot_id` | HTTP с токеном; CLI с явным `user_id` |
| `cancel` | `reservation_id` | HTTP с токеном; CLI с явным `user_id` |

Элемент `slots` содержит `slot_id`, `table_id`, `starts_at`, `ends_at`.
Время — ISO 8601 с явным часовым смещением, например `2030-01-01T18:00:00+02:00`.
Внутри БД время нормализуется в UTC. Пример подготовки есть в функции `seed`
в `restaurant_db/__main__.py`.

Локальный CLI — доверенный административный инструмент с доступом к файлам БД.
Он принимает внутренние команды с явным `user_id`, например `command.json`:

```json
{"op": "reserve", "slot_id": "s1", "user_id": "alice"}
```

Запуск без HTTP и токена:

```powershell
python -m restaurant_db command --data data --request-id my-attempt --file command.json
```

Без `--file` JSON читается из stdin. В этом интерфейсе `request_id`
передаётся аргументом, поэтому файл содержит только объект команды.

## Отмена брони

Для удаления действующей брони отправь `cancel` на тот же `POST /commands`:

```json
{
  "request_id": "alice-cancel-1",
  "command": {"op": "cancel", "reservation_id": 1}
}
```

Подставь `reservation_id` из ответа своего `reserve`. Это номер конкретной
брони, а не столика или слота. Положительное целое число обязательно: `true`,
`1.0` и строка `"1"` не принимаются вместо номера.

Пример PowerShell:

```powershell
$body = @{
    request_id = "alice-cancel-1"
    command = @{ op = "cancel"; reservation_id = $booking.reservation.reservation_id }
} | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:8080/commands -Method Post -Headers $headers -ContentType "application/json" -Body $body
```

Успешный ответ `200` содержит `code: cancelled`, `reservation_id`, `slot_id`
и UTC-время `cancelled_at`. После commit слот доступен новым заявкам.
История остаётся: `inspect` показывает поле `cancelled_at` у каждой брони
(`null` для действующей). `check` считает действующие и отменённые брони отдельно.

Пользователь определяется токеном. Для чужой брони возвращается
`403 reservation_not_owner`. Для неизвестной или уже отменённой брони с новым
ключом — `409 reservation_not_found` или `409 reservation_already_cancelled`.
Любое поле `user_id` во внешней команде отклоняется с `400`.

После потери ответа повтори отмену с тем же ключом и параметрами. Сохраняется
точный результат первоначальной операции; повтор не освобождает слот заново,
если его уже занял другой человек. Для нового бронирования нужен новый ключ.
Повтор старого `reserve` возвращает результат его создания, даже если бронь
позднее отменена; он не возобновляет бронь и не сообщает её текущее состояние.

Отмена одной брони доступна в любое время. Массовой отмены, административного
удаления и восстановления отменённой брони нет. Старые данные читаются без
миграции; старый движок не сможет прочитать новые записи аутентифицированного API.

## Как устроен commit

1. Проверить и нормализовать входные данные.
2. Найти предыдущий результат по `request_id`, если он есть.
3. Проверить бизнес-правила без изменения состояния.
4. Дописать одну транзакцию в журнал, включая команду и её результат.
5. Выполнить `flush` и `os.fsync`.
6. Применить изменения к индексам в памяти.
7. Вернуть результат клиенту.

Выполнение следующей команды начинается после завершения предыдущей.
Между проверкой свободного слота и его занятием другая заявка не вклинивается.
Нет отдельной команды «проверить и потом когда-нибудь записать».

Публикация меняет состояние одного батча. Его слоты заранее подготовлены
полностью; видимость вычисляется по состоянию батча. При перезапуске
незавершённая запись публикации отбрасывается целиком.

Каталог данных содержит `transactions.jsonl` и `owner.lock`.
Каждая строка журнала — транзакция и её SHA-256. Локальный CLI сохраняет формат 1
и прежнее глобальное пространство ключей. HTTP-команды используют формат 2:
он добавляет подтверждённый `actor_id`, ключ идемпотентности — `(actor_id, request_id)`.
Токены в журнал не записываются. Отзыв токена не мешает восстановлению истории.
Перевод строки завершает запись; checksum проверяет её содержимое.
Незавершённый последний фрагмент обрезается при восстановлении.
Повреждённая завершённая запись вызывает отказ открытия, а не скрытую потерю данных.
После полного воспроизведения выполняется обязательный `fsync`, даже если
обрезать ничего не пришлось. Полная запись могла пережить прошлый сбой до
своей синхронизации; повтор заявки не должен обходить гарантию сохранности.
Файл блокировки остаётся после закрытия: владение определяется блокировкой ОС,
а не существованием файла.

Старые журналы не переписываются. Ключи формата 1 изолированы от новых HTTP-ключей:
после обновления старый запрос через API не является продолжением старой CLI/HTTP
попытки только из-за совпадения строки `request_id`. Для нового протокола используй
новые ключи; владельцы уже сохранённых броней остаются прежними. Повторные
локальные команды продолжают видеть прежнюю историю ключей.

## Параметры, выбранные для демо

| Параметр | Значение | Причина и цена |
|---|---|---|
| Адрес сервера | `127.0.0.1` | Локальный учебный интерфейс |
| `--port` | `8080` | Условный порт разработки, можно заменить |
| `--request-timeout` | `5` секунд | Таймаут отдельного socket I/O: незавершённое соединение не должно бесконечно держать единственного обработчика; это не общий дедлайн всей команды |
| `--max-body-bytes` | `1048576` = 1 MiB | Ограничить размер HTTP-запроса; большой батч потребует явного увеличения лимита |
| Listen backlog | `socket.SOMAXCONN` | Используем значение ОС; очередь соединений не гарантирует справедливость или сохранность заявок |
| Синхронизация | После восстановления при открытии и каждой новой валидной команды, включая бизнес-отказы | Стабильные результаты повторов ценой дополнительных дисковых синхронизаций |
| Генератор `--clients` | `20` | Небольшой демонстрационный наплыв, а не расчётная нагрузка |
| Генератор `--timeout` | `30` секунд | Бюджет ожидания клиента в эксперименте, изменяется независимо от серверного таймаута |
| Случайность токена | `32` байта, `256` бит | Явно задаём `secrets.token_urlsafe(32)`; не полагаемся на default библиотеки |
| Срок токена | До ручного отзыва/перевыпуска и перезапуска | Нет автоматического TTL и динамической перезагрузки |

Эти сетевые значения — начальные настройки локального демо, их не подбирали
нагрузочным исследованием. Бизнес-правила от них не зависят.

## Проверка

```powershell
python -m unittest discover -v
```

Тесты проверяют одновременных HTTP-клиентов, одновременные повторы одной заявки,
разрыв соединения, запрет второго владельца, пересечения времени, потерю хвоста
журнала, ошибку `fsync`, принудительное завершение процесса и публикацию,
оборванную на каждой возможной позиции байта. Отдельно проверяются отказ
открытия без успешного `fsync` восстановленной записи, неизменность файлов при
диагностике и коды завершения `check`. Тестовые каталоги создаются
внутри `tests/.test-data` и удаляются после тестов.

Для отмен дополнительно проверяются владелец, повторный захват освобождённого
слота, старые повторы бронирования и отмены, конкурентные HTTP-клиенты, потеря
ответа, ошибка fsync и завершение процесса после записи отмены. Незавершённая
запись отмены проверяется на каждой возможной позиции обрыва.

Аутентификация проверяется на реальном HTTP: отсутствие/подмена/отзыв токена,
дублированные заголовки, попытка передать чужой `user_id`, запрет служебных команд,
повторы после перевыпуска, изоляция ключей разных пользователей и отсутствие
секретов в журнале/логах. Проверяются также смешанный журнал версий 1/2,
обрыв записи, сбой процесса и работа генератора нагрузки с токенами.

## Границы текущей версии

- Можно отменить одну свою бронь; история сохраняется. Один пользователь может
  забронировать несколько разных слотов.
- Слоты одного столика не пересекаются, включая слоты черновиков и других батчей.
  Интервалы полуоткрытые: `[начало, конец)`, соседние интервалы допустимы.
- Публикация ручная. Автоматического открытия по времени, запрета прошлых дат
  и автоматического освобождения по окончании слота пока нет.
- Движок хранит индексы и все ключи идемпотентности в памяти.
  Журнал растёт без ограничения; снимки и очистка ещё не реализованы.
- Транзакции соответствуют фиксированным командам API. Произвольного SQL,
  пользовательских `BEGIN/COMMIT`, репликации и распределённых транзакций нет.
- HTTP — локальный демонстрационный адаптер с персональными токенами, без TLS.
  Регистрации, паролей, автоматического TTL и немедленного отзыва нет. Доверенный
  оператор CLI имеет полный доступ к файлам. `http.server` не является
  промышленным сервером; публичное размещение требует отдельной работы.
- Проверено аварийное завершение процесса. Отключение питания и реальные
  отказы накопителя не испытывались. `fsync` запрашивает синхронизацию у ОС;
  фактическая сохранность зависит от файловой системы и оборудования,
  включая метаданные вновь созданного каталога. Это не обещание полного ACID
  при любых аппаратных отказах.
- SHA-256 не заменяет резервные копии: удаление целых записей, изменение файлов
  внешней программой и намеренная подделка журнала не входят в модель восстановления.

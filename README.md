# Restaurant DB: первая рабочая версия

Учебная специализированная база данных для бронирования конкретного столика
на заранее заданный слот. Python 3.11+, только стандартная библиотека.
PostgreSQL, SQLite и Redis внутри не используются.

Один процесс владеет данными. Один поток последовательно выполняет команды.
HTTP-клиенты могут обращаться одновременно, но движок не выполняет записи
параллельно. Успех бронирования подтверждается после записи журнала и `fsync`.

## Быстрый запуск

Открой PowerShell:

```powershell
cd C:\Users\Maxim\Documents\restaurant-db
python -m restaurant_db demo --data demo-data
```

Демо создаст два столика, подготовит и опубликует батч, забронирует слот за
Алисой, отклонит заявку Боба и повторит заявку Алисы. Затем заново откроет
БД и покажет восстановленные данные. Повторный запуск с тем же каталогом
вернёт сохранённые результаты: идентификаторы заявок демо постоянные.
Даты 2030 года — фиксированные демонстрационные данные.

Просмотр всех данных, включая черновики:

```powershell
python -m restaurant_db inspect --data demo-data
```

Установка пакетов не требуется. Команды запускаются из корня проекта.

## Одновременные пользователи

В первом терминале подготовь отдельную БД и запусти сервер:

```powershell
python -m restaurant_db seed --data race-data
python -m restaurant_db serve --data race-data
```

Во втором терминале, также из папки проекта:

```powershell
python scripts/race.py --clients 20 --slot-id s1
```

Для свежего опубликованного слота ожидается `reserved: 1`, `slot_taken: 19`.
Все клиенты начинают отправку после общего барьера. Потоки используются только
в генераторе нагрузки: сервер и движок остаются однопоточными.
Победитель определяется порядком обработки, а не порядком нажатия кнопок.

Второй независимый эксперимент можно провести со слотом `s2`:

```powershell
python scripts/race.py --clients 20 --slot-id s2
```

Повторный тест уже занятого слота закономерно не получит победителя.
Для следующих прогонов используй новый каталог с данными или новые слоты.
Генератор отдельно считает ошибки транспорта; они не означают «слот занят».
Измеренная скорость локального демо не является оценкой промышленной мощности.
Остановить сервер можно через Ctrl+C. Пока сервер открыт, CLI не сможет
открыть тот же каталог: это намеренная защита от двух владельцев файлов.

## API

`GET /slots` возвращает только слоты опубликованных батчей и их доступность.
Этот ответ не удерживает слот за пользователем.

`POST /commands` принимает JSON:

```json
{
  "request_id": "alice-attempt-1",
  "command": {"op": "reserve", "slot_id": "s1", "user_id": "alice"}
}
```

Пример PowerShell для свежего слота:

```powershell
$body = @{
    request_id = "alice-attempt-1"
    command = @{ op = "reserve"; slot_id = "s1"; user_id = "alice" }
} | ConvertTo-Json
Invoke-RestMethod -Uri http://127.0.0.1:8080/commands -Method Post -ContentType "application/json" -Body $body
```

Ответы: `200` — успешная команда, `409` — бизнес-отказ или конфликт ключа
идемпотентности, `400` — некорректный ввод, `503` — требуется восстановление БД.
Внутри ответа есть поле `code`, например `reserved`, `slot_taken`,
`batch_not_published` или `idempotency_conflict`.
При повторе успешной заявки ответ снова `200`, с той же бронью.

Если ответа нет или пришёл `503`, результат может быть неизвестен. После
восстановления повтори запрос с прежним `request_id` и прежней командой.
Подтверждать пользователю создание брони до успешного ответа нельзя.
После определённого бизнес-отказа новая осознанная попытка получает новый ключ.

Поддерживаемые команды:

| `op` | Остальные поля | Результат |
|---|---|---|
| `add_table` | `table_id`, `name` | Создать столик |
| `prepare_batch` | `batch_id`, `slots` | Атомарно сохранить весь черновик |
| `publish_batch` | `batch_id` | Атомарно открыть весь батч |
| `reserve` | `slot_id`, `user_id` | Попытаться занять слот |

Элемент `slots` содержит `slot_id`, `table_id`, `starts_at`, `ends_at`.
Время — ISO 8601 с явным часовым смещением, например `2030-01-01T18:00:00+02:00`.
Внутри БД время нормализуется в UTC. Пример подготовки есть в функции `seed`
в `restaurant_db/__main__.py`.

Команду можно исполнить без HTTP, записав объект `command` в UTF-8 JSON-файл:

```powershell
python -m restaurant_db command --data data --request-id my-attempt --file command.json
```

Без `--file` JSON читается из stdin. В этом интерфейсе `request_id`
передаётся аргументом, поэтому файл содержит только объект команды.

## Как устроен commit

1. Проверить и нормализовать входные данные.
2. Найти предыдущий результат по `request_id`, если он есть.
3. Проверить бизнес-правила без изменения состояния.
4. Дописать одну транзакцию в журнал, включая команду и её результат.
5. Выполнить `flush` и `os.fsync`.
6. Применить изменения к индексам в памяти.
7. Вернуть результат клиенту.

Выполнение следующей команды начинается после завершения предыдущей.
Между проверкой свободного слота и его занятием другая заявка не вклинивается.
Нет отдельной команды «проверить и потом когда-нибудь записать».

Публикация меняет состояние одного батча. Его слоты заранее подготовлены
полностью; видимость вычисляется по состоянию батча. При перезапуске
незавершённая запись публикации отбрасывается целиком.

Каталог данных содержит `transactions.jsonl` и `owner.lock`.
Каждая строка журнала — транзакция формата 1 и её SHA-256.
Перевод строки завершает запись; checksum проверяет её содержимое.
Незавершённый последний фрагмент обрезается при восстановлении.
Повреждённая завершённая запись вызывает отказ открытия, а не скрытую потерю данных.
Файл блокировки остаётся после закрытия: владение определяется блокировкой ОС,
а не существованием файла.

## Параметры, выбранные для демо

| Параметр | Значение | Причина и цена |
|---|---|---|
| Адрес сервера | `127.0.0.1` | Локальный учебный интерфейс |
| `--port` | `8080` | Условный порт разработки, можно заменить |
| `--request-timeout` | `5` секунд | Таймаут отдельного socket I/O: незавершённое соединение не должно бесконечно держать единственного обработчика; это не общий дедлайн всей команды |
| `--max-body-bytes` | `1048576` = 1 MiB | Ограничить размер HTTP-запроса; большой батч потребует явного увеличения лимита |
| Listen backlog | `socket.SOMAXCONN` | Используем значение ОС; очередь соединений не гарантирует справедливость или сохранность заявок |
| Синхронизация | После каждой новой валидной команды, включая бизнес-отказы | Стабильные результаты повторов ценой дополнительных дисковых синхронизаций |
| Генератор `--clients` | `20` | Небольшой демонстрационный наплыв, а не расчётная нагрузка |
| Генератор `--timeout` | `30` секунд | Бюджет ожидания клиента в эксперименте, изменяется независимо от серверного таймаута |

Эти сетевые значения — начальные настройки локального демо, их не подбирали
нагрузочным исследованием. Бизнес-правила от них не зависят.

## Проверка

```powershell
python -m unittest discover -v
```

Тесты проверяют одновременных HTTP-клиентов, одновременные повторы одной заявки,
разрыв соединения, запрет второго владельца, пересечения времени, потерю хвоста
журнала, ошибку `fsync`, принудительное завершение процесса и публикацию,
оборванную на каждой возможной позиции байта. Тестовые каталоги создаются
внутри `tests/.test-data` и удаляются после тестов.

## Границы первой версии

- Отмен нет. Один пользователь может забронировать несколько разных слотов.
- Слоты одного столика не пересекаются, включая слоты черновиков и других батчей.
  Интервалы полуоткрытые: `[начало, конец)`, соседние интервалы допустимы.
- Публикация ручная. Автоматического открытия по времени, запрета прошлых дат
  и автоматического освобождения по окончании слота пока нет.
- Движок хранит индексы и все ключи идемпотентности в памяти.
  Журнал растёт без ограничения; снимки и очистка ещё не реализованы.
- Транзакции соответствуют фиксированным командам API. Произвольного SQL,
  пользовательских `BEGIN/COMMIT`, репликации и распределённых транзакций нет.
- HTTP — локальный демонстрационный адаптер без аутентификации и TLS.
  `user_id` доверенно передаётся клиентом. `http.server` не является
  промышленным сервером; этот проект не готов к публичному размещению.
- Проверено аварийное завершение процесса. Отключение питания и реальные
  отказы накопителя не испытывались. `fsync` запрашивает синхронизацию у ОС;
  фактическая сохранность зависит от файловой системы и оборудования,
  включая метаданные вновь созданного каталога. Это не обещание полного ACID
  при любых аппаратных отказах.
- SHA-256 не заменяет резервные копии: удаление целых записей, изменение файлов
  внешней программой и намеренная подделка журнала не входят в модель восстановления.
